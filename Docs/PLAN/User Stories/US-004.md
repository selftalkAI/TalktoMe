# US-004 — Goal Adherence Tracking & Adaptive Nudge

**Status:** Draft
**Priority:** Post-MVP (depends on `US-001`, `US-002`; complements `US-003`)
**Related requirements:** `FSD FR-MEM-001` – `FR-MEM-008` (memory extraction/retrieval), `FR-AGT-001` (goal → plan). No FSD requirement yet covers goal *adherence tracking* over time — recommend adding `FR-GOAL-001`+ when this story is picked up (see Notes).
**Related architecture:** `ADD §6` (personal context layers), `ADD ADR-007` (model proposes, deterministic code decides), `TDD §5` (memory write pipeline)
**Related user stories:** `US-001` (Persistent Memory), `US-002` (Memory Layer Mechanism), `US-003` (Emotional Support Agent — Motivate/Reframe aspects)

## Story

As a user who set a goal ("1 hour of gym, every day") and has been falling short of it (15–30 min instead of 60, every day for the last week),
I want the assistant to notice that pattern — grounded in my actual logged sessions, not a guess — and help me either close the gap or adjust the goal,
so that I get a response reflecting what really happened to me, not a generic one-off answer that forgets everything the moment the conversation ends.

## Description

This is explicitly **not** a single request/response exchange. A goal is a long-lived entity that accumulates state across many separate days and app sessions, and the assistant's awareness of it must persist the same way — read from durable storage on every interaction, never re-derived from conversation history or lost when a chat ends.

This story extends the existing memory layer (`US-002`) rather than inventing a parallel mechanism:

- **Structured adherence logging.** A `goal_logs` record (goal reference, date, actual minutes) is written deterministically whenever a session is logged — via chat text (small extraction step, same shape as `SmartAgent._extract_memories`) or a dedicated UI log control. This is the ground truth; the LLM never invents a duration or a streak length later.
- **Persistent goal state**, not just a static memory row. Alongside the existing `goal` memory content, the goal carries `current_streak_under_target`, `last_evaluated_date`, `last_nudged_date`, and a state machine: `on_track → at_risk → renegotiation_offered → adjusted`.
- **A deterministic evaluator** (new module, same layer as `memory_manager.py` — e.g. `goal_tracker.py`) that re-runs on every new log: recomputes the rolling window, updates the streak counter, and decides — by threshold, not by LLM judgment — whether the pattern now qualifies as a shortfall. This mirrors the existing write-gate pattern (`MIN_CONFIDENCE_TO_STORE` in `memory_manager.py`) — the model never grants itself the authority to decide a pattern exists.
- **A gated LLM step**, not a per-log LLM call. Most days, the evaluator updates state and returns a plain deterministic acknowledgment — no model call at all. Only when the threshold is crossed *and* the goal hasn't already been nudged for this same streak (`last_nudged_date` check, preventing daily repetition) does Orchestration build a grounded context bundle (goal + dated logs + computed stats) and call a new `SmartAgent` mode (e.g. `goal_shortfall_response`) — composing language from data that already exists, per `ADR-007`.
- **Renegotiation as correction, not mutation.** If the user agrees to adjust the target, this goes through the existing supersede pattern (`memory_manager.correct`) rather than editing the goal in place, so the original goal and the adjustment are both preserved in history.
- Draws on `US-003`'s Motivate (smallest next step, ask don't lecture) and Reframe (is a rigid "1 hour daily" target itself the problem — Atomic Habits / Mindset framing) aspects when composing the nudge.

## Acceptance criteria

- **Given** a goal exists with a target (e.g. 60 min/day) and a user logs an actual session, **when** the log is saved, **then** a `goal_logs` row is written deterministically (date, actual minutes) before any LLM call happens.
- **Given** a new log is saved, **when** the goal evaluator runs, **then** it recomputes the rolling window and updates the goal's persisted state (streak, last-evaluated date) purely in code — no model call is made unless a threshold is actually crossed.
- **Given** the shortfall threshold has not been crossed, **when** the evaluator finishes, **then** the user receives a plain deterministic acknowledgment only — the LLM is not invoked.
- **Given** the shortfall threshold is crossed for the first time (e.g. 7 consecutive days under target), **when** the assistant responds, **then** it retrieves the goal record and the actual dated log rows from the memory layer, and the LLM call is grounded strictly on that retrieved bundle — it never fabricates the streak length, dates, or durations.
- **Given** the shortfall has already been nudged once (`last_nudged_date` is set for this streak), **when** the same shortfall persists the next day, **then** the assistant does not repeat the same nudge — it only speaks up again on a new state transition (e.g. the streak breaking, or the user re-engaging with the topic).
- **Given** the pattern spans multiple separate app sessions over multiple days, **when** any individual session starts, **then** the assistant's awareness of the streak is read from persisted goal state, not from that session's own conversation history — closing the app and reopening it days later must not lose or reset the streak.
- **Given** the user responds to a nudge by agreeing to adjust the target, **when** the goal is updated, **then** the change is recorded as a supersession (old goal preserved, new goal linked via `supersedes_id`) and the goal's state resets (`adjusted`, streak cleared) rather than silently overwriting the original goal.
- **Given** the response is composed, **when** it addresses the shortfall, **then** it follows `US-003`'s Motivate/Reframe ordering — asks rather than lectures, and offers the smallest workable next step rather than pushing to immediately hit the original 60-minute target.

## Out of scope for this story

- A background scheduler/cron that evaluates goals on days with no logging activity at all — this story's evaluator only re-runs when a new log arrives (sync, same trigger point as `memory_manager.remember_from_text` today). True proactive "you didn't even log anything in 3 days" nudging requires new scheduling infrastructure that doesn't exist yet in `orchestration-service`, and is tracked as a follow-up, not part of this story.
- Goal types beyond a single daily-duration target (e.g. weekly totals, non-duration goals like "read 10 pages") — the mechanism should generalize, but this story's acceptance criteria are scoped to the duration-per-day case.
- Any UI design for the dedicated log control — this story only requires that a log, however captured, reaches the same `goal_logs` write path.

## Notes

- **New FSD requirement recommended:** none of the existing `FR-MEM-*` requirements cover adherence-over-time tracking against a target; add `FR-GOAL-001`+ (adherence logging, deterministic shortfall evaluation, anti-repeat nudging) to the FSD when this is implemented, so the requirement is traceable the same way `US-003` flagged new memory types for `FR-MEM-002`.
- **Schema additions needed:** a `goal_logs` table (or equivalent), and new persisted fields on the goal record (`current_streak_under_target`, `last_evaluated_date`, `last_nudged_date`, lifecycle state) — none of which exist in the current `memories` schema (`TDD §21` / `db.py`) today.
- **Wiring point:** the evaluator hooks in right after a moment/log is saved, the same place `memory_manager.remember_from_text` is called from `POST /api/v1/moments` today (`main.py`) — no new API surface required for the detection path itself.
