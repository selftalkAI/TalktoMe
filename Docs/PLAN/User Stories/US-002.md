# US-002 — Creation of Building Memory Layer Mechanism

**Status:** Draft
**Priority:** MVP / must-have
**Related requirements:** `FSD FR-MEM-001` – `FR-MEM-011`
**Related architecture:** `ADD §6` (personal context layers), `ADD §32.1` (why personal context has multiple layers), `TDD §4` (core data model), `TDD §5` (memory write pipeline), `TDD §6` (memory retrieval pipeline), `TDD §21` (schema sketch)

## Story

As an engineer building selfie.Me,
I want a concrete memory layer mechanism (schema, write pipeline, retrieval pipeline, and the service/module boundaries around them),
so that "durable memory" is an enforced architectural layer with real rules — not something implicitly re-derived ad hoc every time a feature needs to remember something about a user.

## Description

`US-001` describes the user-facing outcome (the assistant remembers things). This story is the underlying mechanism that makes that possible: the actual data model, module boundaries, and pipeline stages a memory record passes through, from raw text to governed, retrievable memory.

Concretely, this covers:

- A `memories` table (or equivalent store) with the fields the ADD/TDD require: type, canonical content, explicitness, confidence, sensitivity tier, status, provenance (source type/id), supersession link, and timestamps.
- A **write pipeline**: candidate extraction → schema validation/normalization → classification → policy decision (store / require confirmation / transient-only / reject) → deduplication → persist → (async) embed and index.
- A **retrieval pipeline**: ownership + status filtering *before* similarity ranking (never after), then relevance scoring, then a bounded, provenance-carrying context bundle handed to callers.
- Clear module ownership: extraction/classification is a model-driven step (the Agentic Service proposes), while the write-gate decision and all persistence are deterministic application logic (the Orchestration Service decides and owns), per `ADR-007` — the model never grants itself storage authority.
- Embeddings/vector index entries are treated as derivative and rebuildable from the canonical memory table, never the sole copy (`ADD §10.1`, `ADD ADR-005`).

## Acceptance criteria

- **Given** a memory record's fields, **when** inspected, **then** it includes type, content, explicitness, confidence, sensitivity tier, status, provenance (source), and — where applicable — a link to the memory it superseded.
- **Given** a piece of source text (a moment or conversation turn), **when** it passes through the write pipeline, **then** each candidate is validated and normalized before any storage decision is made, and malformed candidates are rejected rather than stored as-is.
- **Given** a stored memory's embedding is lost, corrupted, or the embedding model changes, **when** the index is rebuilt, **then** it is regenerated entirely from the canonical memory records with no loss of durable data.
- **Given** a retrieval request for a user's memories, **when** the query executes, **then** ownership and active-status filtering happen before similarity ranking — a similar-but-deleted, suppressed, superseded, or cross-user record can never enter the ranked results.
- **Given** the extraction step (model-driven) proposes a candidate, **when** the write-gate evaluates it, **then** the storage decision (active / requires confirmation / not stored) is made by deterministic code, not by trusting the model's own confidence claim uncritically.
- **Given** two components need to remember something about a user, **when** each integrates with this mechanism, **then** neither needs to invent its own ad hoc persistence — both go through the same write and retrieval pipeline.

## Out of scope for this story

- The Belief layer (evidence-weighted, continuously-revisable propositions) — a distinct mechanism built on top of, not instead of, this one (`ADD §6`).
- Migrating off SQLite/Chroma to Postgres/pgvector — this mechanism is designed to be portable to that store later without changing its pipeline stages or module boundaries (`ADD §5.2` scale-out triggers).
- Consent/category opt-in UI — the write-gate encodes the deterministic default rules; the user-facing controls are a separate story.

## Notes

This is the technical counterpart to `US-001`: US-001 is "what the user experiences," US-002 is "the mechanism that makes it true and keeps it honest" — matching the ADD's own separation between product requirement and enforceable architecture.
