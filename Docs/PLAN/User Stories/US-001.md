# US-001 — Persistent Memory

**Status:** Draft
**Priority:** MVP / must-have
**Related requirements:** `FSD FR-MEM-001` – `FR-MEM-011`, `FR-CONV-005`, `FR-CONV-006`
**Related architecture:** `ADD §6` (personal context layers), `ADD §13` (privacy gates), `TDD §5` (memory write pipeline), `TDD §6` (memory retrieval pipeline)

## Story

As a user of selfie.Me,
I want the assistant to remember durable facts, preferences, and goals I've shared across conversations,
so that I don't have to repeat myself and future interactions feel personalized rather than starting from zero each time.

## Description

Today, what a user shares (a "moment") is captured as a raw record, and only a single, overwritten snapshot (mood/context/narrative focus) persists on their profile. There is no durable, typed, correctable memory that survives and accumulates over time.

This story introduces a governed memory layer: candidate facts are extracted from what the user says, classified by type and sensitivity, and — depending on confidence and sensitivity — either stored as active memory or held for the user's confirmation. Stored memories can later be corrected (superseding the old value, not erasing history) or deleted, and are used to ground future responses.

## Acceptance criteria

- **Given** a user shares something durable and reusable (e.g., "I prefer short, direct replies"), **when** the interaction completes, **then** a memory candidate is extracted, classified (type, explicit/inferred, confidence, sensitivity tier), and — if it clears the write gate — stored as an active memory with provenance back to the source message.
- **Given** a candidate memory is classified as highly sensitive (T3: health, financial, government ID, sexual orientation, immigration, legal), **when** it is extracted, **then** it is never auto-stored as active; it requires explicit user confirmation first.
- **Given** an active memory already exists with the same normalized content, **when** the same fact is restated, **then** no duplicate memory is created.
- **Given** a user views their stored memories, **when** they correct one, **then** the old value is marked superseded (not deleted) and the corrected value becomes the current active memory.
- **Given** a memory has been deleted or suppressed, **when** any future retrieval or conversation runs, **then** that memory is never returned or used to ground a response.
- **Given** a user asks something where a stored memory is relevant, **when** the assistant responds, **then** the response is grounded using that memory and the memory basis is identifiable (not silently invented).
- **Given** a fresh, explicit instruction conflicts with an older stored memory, **when** the assistant responds to the current request, **then** the fresh instruction takes precedence for that response.

## Out of scope for this story

- Belief layer (inferred, continuously-revisable propositions distinct from memory) — tracked separately.
- Cross-device/session sync beyond what the existing profile-scoped storage already provides.
- Full consent/category opt-in UI — this story assumes the deterministic write-gate rules stand in for that until the UI exists.
